# 5. Request

Follow the token transport convention established by login and refresh.

If refresh tokens are currently sent in the request body, logout may use:

```json

}
```

If refresh tokens are stored in an HTTP-only cookie, logout should operate on that cookie and clear it.

If the existing architecture uses authenticated user/session information instead, follow that implementation.

**Do not introduce a new token transport mechanism for logout.**

# 8. Refresh-token revocation

This is the most important part of logout.

If refresh tokens are persisted or associated with a session:

```text
logout
  ↓
find active refresh token/session
  ↓
revoke/invalidate
  ↓
future /auth/refresh
  ↓
reject revoked token
```

After successful logout, the previously valid refresh token must no longer be usable if the current architecture supports server-side revocation.

If refresh-token rotation is already implemented, make logout compatible with it.

Do not accidentally revoke every session belonging to the user unless that is the existing product behavior.

Prefer revoking the **current session/token** when the architecture supports multiple sessions.

---

# 9. Access token behavior

Understand the difference:

```text
Access Token
    ↓
short-lived
    ↓
usually stateless
```

and:

```text
Refresh Token
    ↓
longer-lived
    ↓
used to obtain new access tokens
```

If the current architecture uses stateless access tokens, logout does not necessarily make an already-issued access token immediately invalid.

That is acceptable if it matches the existing architecture.

The critical requirement is:

```text
After logout:
the refresh mechanism must no longer allow
the logged-out session to obtain new access tokens
```

Do not invent an access-token blacklist unless the existing architecture explicitly uses one.

Document this behavior clearly.
