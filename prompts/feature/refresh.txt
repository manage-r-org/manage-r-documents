# 3. Endpoint

Implement:

```http
POST /api/v1/auth/refresh
```

Its purpose is:

```text
Client has a valid refresh token
            ↓
send refresh token
            ↓
backend validates it
            ↓
identify user/session
            ↓
issue new access token
            ↓
optionally rotate refresh token
            ↓
return authentication tokens
```

# 6. Token validation

The refresh endpoint must verify that the supplied refresh token is legitimate.

At minimum:

```text
refresh token
      ↓
verify signature
      ↓
verify expiration
      ↓
extract identity
      ↓
validate token/session state
      ↓
issue new access token
```

Use the configured:

```text
JWT_REFRESH_SECRET
JWT_REFRESH_EXPIRATION
```

Do not use the access-token secret to validate refresh tokens.

Do not use the access-token expiration for refresh tokens.

# 9. Refresh-token rotation

Inspect the current architecture before deciding whether to rotate refresh tokens.

If the project already supports refresh-token persistence/session tracking:

```text
old refresh token
        ↓
validate
        ↓
invalidate/rotate old token
        ↓
generate new refresh token
        ↓
persist new token/session state
```

Implement rotation according to the existing design.

If refresh tokens are currently stateless and there is no persistence/revocation mechanism, do **not** fake rotation by merely generating another token while leaving the old token permanently valid.

Instead, preserve the current architecture and clearly document the limitation.

If a secure rotation mechanism requires a database change, make the smallest reasonable change and explain exactly why it is required.

# 15. Security requirements

Ensure:

* refresh tokens are never logged
* JWT secrets never appear in logs or responses
* expired refresh tokens are rejected
* invalid signatures are rejected
* wrong token type is rejected if the project distinguishes token types
* access-token and refresh-token secrets remain separate
* access-token and refresh-token expirations remain separate
* client cannot choose the user
* client cannot choose the role
* password information is never involved in the refresh response
* raw Prisma/database errors are not exposed
* existing rate limiting remains active
* existing Helmet/CORS/security configuration remains untouched

If refresh tokens are persisted, never store them as plain text if the existing security design supports hashing/token fingerprints.

Follow the existing architecture rather than introducing unnecessary security mechanisms.

# 16. Authentication flow

Make sure the implementation fits this complete authentication lifecycle:

```text
REGISTER
   ↓
Create account
   ↓
LOGIN
   ↓
Verify credentials
   ↓
Access Token + Refresh Token
   ↓
Access token expires
   ↓
POST /auth/refresh
   ↓
Validate Refresh Token
   ↓
Issue new Access Token
   ↓
Client continues using API
```

The refresh endpoint should **not require the normal access-token guard**, because its purpose is to obtain a new access token after the access token has expired.

Do not accidentally protect `/auth/refresh` with `JwtAuthGuard` if that would require a valid access token.
